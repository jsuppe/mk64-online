What’s in this build?

Online menu & rooms

Host a room, join by code, or find public rooms. Player names and lobby presence are shown in-game; the host starts the session. Peers need compatible builds.

Shared race simulation

Peers exchange controller inputs and run the simulation locally. The showcased race tests use two or four separate emulator instances—not four views from one emulator.

Balloon Battle

Big Donut has four-peer development footage. Block Fort, Double Deck, and Skyscraper are in the qualification plan; there is no all-arena pass yet.

Replay & diagnostics

The development code records applied inputs and simulation hashes. Spectator/replay camera controls exist in the source; their presence is not a blanket player-experience sign-off.

UNDER THE HOOD

Inputs over the network. Game state locally.

Deterministic lockstep

The game maintains a shared input history. Each participant sends its buttons and stick values; every peer applies the same inputs to the same logical frame. A missing required input stalls simulation advancement rather than guessing the remote kart’s movement.

controller → input ring → shared logical frame → local MK64 simulation

This is not a video stream or a claim of zero-latency rollback. Network delay affects control latency and stalls. The source negotiates input delay from lobby RTT; no end-to-end latency benchmark is claimed here.

v77 native race automation

Automated race clients send a reserved input marker. All peers convert that slot from PLAYER_HUMAN to PLAYER_CPU on the same applied frame. The controller lane is neutral while native CPU AI drives the kart. The replay tape preserves the marker.

Human participants remain controller-driven. Battle does not use native race CPU navigation: it keeps the older waypoint fallback. That is why race and Battle automation need separate fixes.

v77 keeps the product’s three-lap rule in automated tests, tracks AI participation from shared applied inputs, and holds results until every participating slot finishes. Cinematic cameras are allowed after an actual finish—not halfway through an active race.

v77 qualification: full three-lap runs, four peers

Runs 1–3 compared 9,241 / 7,664 / 8,040 shared frames, with zero divergence in each run. Every automated participant reached lap count 3, with no premature finish flags or non-chase camera samples while actively racing. Position telemetry also checks actual displacement, not speed alone.

The qualification notes record repeat-run results, sample cadence, checksums, and the limits of this evidence. This does not establish all-course, Battle-driver, mixed-human, or physical-console compatibility. Read the test report ↗

Build & setup notes

Required components

  1. MK64 game source
    jsuppe/mk64-netpak64 · netpak64 branch. The qualified demo source cut is tagged v77.
  2. NetPak64-enabled emulator
    ares-netpak64. Stock ares is not a drop-in replacement for the networking device implementation.
  3. Accessible relay
    np64-relay. Peers must use a compatible networking stack and matching session configuration.
  4. Your own game assets
    The source repository does not include the game’s assets. Extract them from your own lawful game copy. ROM files are not hosted here.

The build system supports multiple original revisions, but these showcase tests use the US development build. Do not assume PAL, arbitrary emulator revisions, or mixed game builds will interoperate.

Exact end-user installation and relay configuration are not yet published as a verified walkthrough. Use the repository instructions and release manifest for development; don’t treat this page as a complete setup recipe.

OPEN / PLAYER CAMERA

Joiner view & orbiting

The v76 automated build finished after one lap and entered cinematic mode. v77 uses three laps and waits for all automated participants before results. This fixes the reproduced demo lifecycle bug; normal human joiner cameras and other courses remain separate regression work.

OPEN / AUTOMATION

Wall contact & idle racers

Four-peer native CPU demos have completed standard three-lap Mario Raceway runs. This is limited course/mode coverage, not an all-course driver pass. Battle’s waypoint driver still needs arena-aware navigation and item/opponent strategy.

RETEST / PLATFORM PARITY

Big Donut & lifecycle

The inherited manifest lists a console-only kart-1 physics desync on Big Donut and pause-at-end issues. v77’s emulator race tests do not close them. The legacy results class label also needs review. Physical hardware remains unverified end-to-end.

Qualification plan / what gets tested next?

Mario Raceway now has full three-lap, all-seat automated validation. Next: human/mixed-seat regressions, traffic/branches/rescue stress cases, all 16 race courses, and four Battle arenas. The native CPU demo does not establish human-controller parity or hardware readiness.

Full scenarios also cover items, forced recovery, mixed human/automated seats, pause/resume, results/rematch, and supported leave/drop behavior. Driving, camera, simulation, and media each get a separate verdict.
